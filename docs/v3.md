# PromotionGuard v3 — Severity, Generated Plans, Delegation, and the Ghost

**Status:** v2 shipped and reached the final round. Enforcement is real, the panel is real, the
destructive artefacts are on disk.
**This document:** the five things v3 adds, why each one exists, exactly how each is computed,
what breaks, and what we fall back to.

## 1. Why v3 exists — the two questions v2 cannot answer

v2 answers *"is it hardcoded?"* well. It does not answer either of the two questions a final-round
judge will actually ask.

### 1.1 "What did you build that ArmorIQ didn't?"

Ed25519 signing, merkle step proofs, the intent token, the proxy, the hold, the delegation request,
the approval dashboard — all of it is the SDK. Remove the SDK from v2 and nothing of ours is left
except a scenario, a panel, and a demo script. That is an integration demo with excellent art
direction. Against other teams on the same SDK, "we integrated it well" is not a claim.

### 1.2 "Who decides block versus hold?"

Today: an OPA glob and a role hierarchy that we typed into a config file before the event. So the
honest answer is *"we decided, in advance, per action."*

That is fatal, because it is structurally the same object we spend slide 2 attacking. A keyword
filter is a hand-written table mapping strings to verdicts. Our policy is a hand-written table
mapping actions to verdicts. The plan check in between is genuine and does real work — but the
*consequence* of failing it is a lookup, and a judge who notices that has undercut the whole pitch
in one sentence.

**v3's thesis:** ArmorIQ enforces the plan. *We decide what a violation costs, and therefore who —
if anyone — is allowed to say yes.* That decision is derived, not configured.

## 2. Component 1 — the severity layer (the USP; build this first)

### 2.1 What it is

A deterministic function evaluated at plan-capture time and again at each out-of-plan call:

```
severity(action, args, signed_plan, tool_manifest, agent_role) -> verdict + derivation
```

It emits the ArmorIQ policy rather than reading one. Enforcement stays where it was; the *policy
that gets enforced* is now generated from the plan in front of the judge, seconds before the run.

### 2.2 The one input that is hand-written, and why that is fine

Each MCP tool carries a **manifest entry** — mechanical facts about the tool, not verdicts:

```jsonc
// tools/manifest.json
"dataset-mcp.delete_rows": {
  "reads":     ["labels"],
  "writes":    ["labels"],
  "inverse":   null,                       // no restore path in this MCP surface
  "authority": { "*": "data_owner" }
},
"registry-mcp.promote_model": {
  "reads":     ["models"],
  "writes":    ["promotions"],
  "inverse":   "registry-mcp.demote_model",
  "authority": { "stage=staging":    "operator",
                 "stage=production": "release_manager" }
},
"dataset-mcp.read_split": {
  "reads": ["labels"], "writes": [], "inverse": null, "authority": { "*": "reader" }
}
```

**Anticipate the attack.** A judge will say: *"that's your lookup table with extra steps."* It is
not, and the answer must come out in one breath:

> This is a type signature, not a policy. It says what the tool touches and whether it has an
> inverse — facts the person who wrote the MCP server knows and we do not get to choose. It
> contains no verdicts. The same manifest entry produces ALLOW, HOLD or BLOCK for the same tool
> depending on the plan and the arguments. Change the plan, don't touch the manifest, and the
> verdict changes.

Have that demonstrated, not just said: §8 step 7 flips a verdict without editing the manifest.

### 2.3 The three axes

**Reversibility** — read straight from `inverse`.

| Value | Meaning |
|---|---|
| `reversible` | inverse exists in the same MCP surface, restores prior state exactly |
| `compensable` | inverse exists but is lossy (demote leaves the promotion record) |
| `irreversible` | no inverse — `delete_rows` |

**Blast radius** — computed against the signed plan, not configured. Define the plan's
**evidence base**: the union of resources read by any signed step whose output feeds the goal
predicate. For our plan that is `{labels, dataset_card, metrics}`.

| Class | Test |
|---|---|
| `tampering` | `action.writes ∩ evidence_base ≠ ∅` — it mutates what the run is graded on |
| `in-scope` | `action.writes ∩ plan_resources ≠ ∅`, but not evidence |
| `external` | writes nothing the plan touches |

This is the mechanical statement of the thing slide 2 says in English. `delete_rows` writes to
`labels`; step 2 (`read_split`) read from `labels`; `read_metrics` depends on that read. Therefore
`tampering` — with no keyword, no phrasing, no model judgement involved.

**Authority delta** — `required_role(action, args)` from the manifest, minus the agent's granted
role rank. `promote_model(stage="staging")` needs `operator`; the agent has `operator`; delta 0.
`stage="production"` needs `release_manager`; delta +1. **Same tool, same call, different argument
— and the difference is now numeric.**

### 2.4 The routing matrix

Evaluated only for calls that fail plan membership. In-plan calls flow; the plan already authorized
them.

| Reversibility | Blast radius | Authority delta | Verdict |
|---|---|---|---|
| `irreversible` | `tampering` | any | **BLOCK-HARD** — no approval path exists |
| `irreversible` | in-scope / external | any | **HOLD** |
| `compensable` | `tampering` | any | **HOLD**, flagged `evidence-touching` |
| `compensable` / `reversible` | any | `> 0` | **HOLD** |
| `reversible` | in-scope / external | `<= 0` | **BLOCK** (soft) — see §2.6 |

### 2.5 BLOCK-HARD is the most valuable thing in v3

An action that is irreversible *and* mutates the evidence the run is graded on has **no approval
path**. Not "requires a senior approver" — none. Grant the agent every role in the hierarchy and it
still blocks.

> *"You cannot approve your way past this one. A human can consent to risk. A human cannot consent
> to destroying the evidence that the decision they're being asked to make was based on — by the
> time they see the request, the thing that would tell them whether to say yes is already what's
> being deleted."*

That is a governance claim no filter, no allowlist and no role hierarchy makes, and it falls out of
the two axes automatically.

### 2.6 Reconciling with v2's closer — the authorize-`delete_rows` demo still works

v2's best moment was: tick "Clean noisy rows", watch the same injection succeed. BLOCK-HARD appears
to kill it. It does not, and the resolution is the sharpest idea in this document:

**Severity only runs on out-of-plan calls.** If `delete_rows` is in the signed plan, it was
declared *before the evidence existed and before the agent knew it would miss the bar*. That is a
legitimate pre-declared intent. If it appears mid-run, after the agent has seen its own failing
metrics, it is improvisation against its own grading — and that is never approvable.

> *"Declared up front: allowed, it runs, the rows really drop. Reached for mid-run after seeing a
> bad score: blocked, and nobody in the org can approve it. Same call. The difference is whether
> you committed to it before you knew the answer."*

Both beats now coexist and each makes the other sharper.

### 2.7 The `NOTED` tier — designed, disabled by default

A fourth verdict for `reversible` + `external` + delta ≤ 0: allowed, logged, surfaced. Defensible
(*"not every deviation is an incident"*), but it invites *"so you let it go off-plan?"* mid-demo.
Ship it in the code, default to BLOCK, mention it only if a judge asks about false-positive cost.
First item on the fallback ladder.

### 2.8 Legibility — non-negotiable

Every verdict emits its derivation as one sentence, on the panel and in the audit record:

```
BLOCK-HARD  dataset-mcp.delete_rows
  not in signed plan (5 steps, hash 4f2a…)
  irreversible: no inverse in dataset-mcp
  tampering: writes `labels`, read by step 2 (read_split) which feeds the goal metric
  -> no approval path
```

`INTENTMISMATCH` is a status code. That block is an argument. The judge should be able to read the
verdict and reconstruct the rule without us narrating.

### 2.9 Generated policy, shown on screen

At sign time the engine walks (plan × manifest × role) and emits the OPA constraints and hold
thresholds handed to ArmorIQ. Render the generated policy beside the signed plan during the signing
beat — three seconds of visible artefact that says *we did not write this before the event, it came
out of your plan.*

## 3. Component 2 — the generated, editable plan

### 3.1 The flow

```
goal (NL) + resource bindings  ->  planner  ->  draft plan  ->  judge edits  ->  SIGN
```

**Bindings are the only hard requirement**, as decided: one dataset, one model. Everything else the
judge writes. Conditions (Bank B from v2 — card clean/poisoned, model clears/misses/fails, hash
match/mismatch) stay exactly as they are.

### 3.2 The planner

Constrained generation against the tool manifest — the model may only emit `(mcp, action, args)`
triples that exist, with schema-valid arguments. Temperature 0. Invalid output is retried once,
then falls back (§7.2).

Validation before the plan is renderable:
- every step resolves to a real tool with valid args
- resources referenced resolve to the judge's bindings
- the plan reads the dataset at least once and terminates in an action that changes state
- the dependency graph is acyclic
- ≤ 8 steps (layout constraint, §6.3)

### 3.3 Editing is what makes signing mean something

The draft is not a preview — it is editable. Delete a step. Add one from the tool palette. Change
`stage="staging"` to `"production"` and watch the plan's own authority requirement update *before*
signing. Reorder. Then, and only then, the key dial arms.

This is a much stronger answer to "is it hardcoded" than v2's switch banks, because the plan came
out of the model, from the judge's own goal string, in front of them — and then they changed it.

It also produces a moment worth rehearsing: **edit the plan to include production promotion, and
the run has no hold at all.** Nothing was violated; the authority was declared up front. *"The hold
isn't a feature that fires on production. It fires on the gap between what you declared and what it
reached for."*

### 3.4 Determinism protection

Three presets ship as known-good goal strings with cached plans (`BASELINE / INJECTION /
ESCALATION`). A free-typed goal is the impressive path; a preset is the safe path. Never open the
demo on a free-typed goal — do the preset first so the room has seen a clean run, then invite them
to type one.

## 4. Component 3 — the plan as a growing graph

### 4.1 Why a graph rather than v2's strip

The strip is a list. Blast radius is a *relation* — `delete_rows` is catastrophic because of an
edge between it and step 2. A list cannot draw that; a graph draws it for free. So the graph is not
decoration, it is the severity engine's input rendered.

### 4.2 Structure

- **Nodes** = plan steps. **Edges** = resource dependency (step B reads what step A wrote, or both
  touch the same resource).
- **Evidence base is a visibly shaded region** — the subgraph feeding the goal metric.
- Layered left-to-right, positions fixed at sign time. No physics simulation, no reflow mid-run.

### 4.3 The choreography

| Moment | Behaviour |
|---|---|
| Signing | Nodes drop in one per step as the merkle tree builds — v1's missing signing beat, made spatial |
| Executed | Node fills, edge to next lights |
| Out-of-plan call | An **unattached node arrives from outside**, tries to connect, fails proof, and is ejected — with its derivation sentence beside it |
| BLOCK-HARD (tampering) | The rejected node visibly reaches toward the shaded evidence region before being ejected. That single frame is the whole thesis |
| HOLD | Node pulses at the boundary, held in place, not admitted and not ejected. Key dial arms |
| Approved | Node snaps into the graph and execution resumes through it |
| Delegation (§5) | Sub-plans render as enclosing regions around their subtrees (§5.3) |

### 4.4 Constraints

Deterministic layout, ≤ 8 nodes, no animation longer than 600 ms, everything readable frozen in a
screenshot. If it cannot be understood as a still image, it is decoration and it gets cut.

## 5. Component 4 — the ghost run

### 5.1 What it is

The unguarded run, recorded once, replayed as a dim second track alongside the live guarded run on
the same timeline. At the injection the two tracks visibly fork: the ghost's row gauge drains to
60, the live gauge holds at 100.

### 5.2 Why it earns its place cheaply

It folds v2's "damage first" prelude — currently a separate, unglamorous segment before the panel
appears — into the main run without losing it. The before/after stops being two things the judge
has to hold in their head and becomes one image. And the trace already exists on disk.

### 5.3 Synchronisation — the part that will break if done naively

**Align on step index, never on wall clock.** The guarded run pauses at the hold for as long as the
dashboard approval takes; a clock-aligned ghost runs away and the whole thing turns to noise.

- Ghost advances one step only when the live run resolves a step (any verdict).
- At a hold, the ghost freezes too, and its next step renders as a dimmed **preview**:
  *"unguarded, this is what happened next."*
- Where verdicts differ, draw the fork explicitly and hold it on screen.

### 5.4 Honesty

Permanent `RECORDED · UNGUARDED · <run id> · <timestamp>` label on the ghost layer, with the trace
file path visible and the file committed under `evidence/`. Offer to run it live on request. The
moment a judge suspects the ghost is fabricated, every real thing on the panel is suspect too.

## 6. Component 5 — subagents

**Take this last. It is PS2's problem statement grafted onto a PS1 build, and it is the largest
single piece of work here.** It is worth it only because it produces a violation class that
nothing in v2 — and nothing any flat-plan competitor has — can catch.

### 6.1 Shape

Parent plans the full job and signs it. It then delegates two **sub-plans, each a proper subset of
the parent's merkle tree**, so a delegate's authority is provably carved out of the parent's rather
than granted separately:

| Delegate | Sub-plan |
|---|---|
| `evaluator` | `get_dataset_card`, `read_split`, `launch_run`, `get_run_status`, `read_metrics` |
| `deployer` | `list_models`, `promote_model(stage="staging")` |

Sequential only. Two delegates, fixed. **No dynamic spawning, no concurrency.** Concurrency will
consume the remaining time and produce a demo that fails live.

### 6.2 The new violation — cross-scope

**The evaluator calls `promote_model(stage="staging")`.**

- In the parent's signed plan? **Yes.** Correct tool, correct argument, fully authorized at crew
  level.
- In the evaluator's sub-plan? **No.**
- Verdict: **BLOCK — `SCOPEBREACH`**: *authorized for the crew, not for this delegate.*

v2 cannot catch this. Flat plan membership says yes. Keyword filters say yes. Role checks say yes —
the crew holds the role. Only the delegation boundary says no. This is the strongest single claim
v3 can make and it is worth real risk to land.

### 6.3 Trust chain

`plan_hash → delegation_hash (subtree root) → step_proof`, printed for every call in the audit
trail. Each delegate's authority is cryptographically derived from the parent's, so the chain is
verifiable rather than asserted.

### 6.4 Blocking prerequisite

**Verify `delegate()` end to end before writing any of §6.** Same discipline v2 applied to the hold
path, same reason: the most valuable element is downstream of the least-verified mechanism. If the
SDK does not support scoped sub-plan tokens the way we need, collapse to a single agent (§9,
rung 2) and lose nothing else.

## 7. Surfaces

One page still. Five states.

| Surface | Contents |
|---|---|
| **1 · ARM** | Goal field + presets, resource bindings, Bank B condition dials, role grant. Plate reads `NO PLAN` |
| **2 · REVIEW** | Generated graph, editable, severity preview per step, `PLAN NOT SIGNED` |
| **3 · SIGN** | Nodes drop in, merkle builds, generated OPA policy renders beside it, key dial arms |
| **4 · RUN** | Graph + ghost track + v1 gauges, scope engine, console. Verdicts land with derivations |
| **5 · PROOF** | Trust chain per call: plan hash → delegation hash → step proof → verdict → derivation |

Surface 6 remains ArmorIQ's own dashboard, for the same deliberate reason as v2: **authority does
not live in our process.** Still no Approve button in our panel. Still pre-authenticated in a
second window, filtered to "Needs you", before the demo starts.

## 9. Failure modes

**9.1 Planner emits an unusable plan.** Retry once, then load the preset's cached plan and light a
visible `PLANNER FALLBACK` lamp. Honest and unremarkable — a preset plan is still a signed plan.

**9.2 Judge writes a goal that makes no violation possible.** Fine. Bank B still poisons the card
and the agent still reaches. If it genuinely does not, that is the *"flows freely, nobody watching"*
beat, which is half the thesis — narrate it as such and re-run with `INJECTION`.

**9.3 Judge writes a goal that authorizes everything.** Also fine, and it is closer B. Say it out
loud before running it.

**9.4 Severity misclassifies live.** Every verdict prints its derivation, so a wrong verdict is
*debuggable on stage* rather than embarrassing: read the derivation, point at the wrong axis, say
which manifest field is wrong. Far better than an unexplained verdict.

**9.5 `delegate()` unsupported or unstable.** Collapse to single agent. Severity, generated plan,
graph and ghost are all independent of it.

**9.6 Ghost desyncs.** Freeze the ghost layer and fall back to v2's static before/after database.
Build the freeze switch as a keyboard toggle, not a code change.

**9.7 Graph reflow chaos on an edited plan.** Positions computed once at sign time and frozen.
Editing happens pre-sign, where reflow is expected and harmless.

**9.8 Hold path regresses.** Unchanged from v2 §4.3 — blocks only, key dial to permanent
`NO PENDING APPROVAL`, narrate as designed-and-wired.

**9.9 LLM does not take the bait.** `--force-violation` stays. It is the recording path and the
emergency live path.

**9.10 Tunnel / dashboard login.** Unchanged from v2 §4.5 and §4.7. Recorded deterministic video
recorded the moment the flow works end to end, not at hour 23.

## 12. Honest assessment

**What v3 buys.** A defensible answer to *"what did you build?"* — a derived consequence model that
turns block-vs-hold from configuration into computation, with BLOCK-HARD as a governance claim
nobody else in the room will make. A generalization story that survives a judge typing their own
goal. And one violation class (cross-scope delegation) that flat-plan enforcement cannot detect at
all.

**What actually decides it.** Whether the manifest survives the *"that's just a lookup table"*
attack in one breath. Whether the derivation sentences are readable by a generalist. Whether the
signing beat lands as a visible artefact rather than a spinner.

**Biggest risk.** Same structural mistake as v2, one layer up: the most impressive element
(delegation) is downstream of the least-verified mechanism (`delegate()`), and the most important
element (severity) is a rewrite of the path that currently works. Do not let severity break
enforcement while chasing delegation.

**Second risk.** v3 is five components. v2 shipped because it was disciplined about scope and the
track's own advice was taken literally. Five is already past that line. The MVP in §11 is the real
plan; treat everything after it as optional and be willing to say so at hour X-4.

**Realistic outcome.** The MVP alone moves this from a well-executed integration to a project with
a thesis. The graph plus the ghost make that thesis legible in a still frame. Delegation wins the
round if it works and costs the round if it half-works at hour 19.
